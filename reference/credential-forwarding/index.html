Azure Credential Forwarding

Use DefaultAzureCredential inside Docker containers during local development. No configuration files, no service principals, no secrets.

The Problem

If you've ever tried to use DefaultAzureCredential inside a Docker container during local development, you've hit this wall: it doesn't work.

The Azure Identity SDKs rely on host-level credentials — Azure CLI tokens, environment variables, managed identity endpoints — none of which exist inside a container. This is a long-standing pain point across every Azure SDK: .NET, Python, Java, Node.js, and Go.

What developers do instead (and why it's painful)

  • Create service principals — Operational overhead, secrets to manage, and they expire
  • Use connection strings — Secrets in config files, hard to rotate, easy to leak
  • Mount ~/.azure into the container — Insecure, leaks entire Azure config
  • Skip Azure entirely in local dev — Dev/prod divergence, bugs caught late

Credential forwarding solves this by securely proxying your host credentials into containers automatically.

How It Works

Credential forwarding creates a secure bridge between the container and your host's Azure credentials using mutual TLS (mTLS).

Architecture

Step-by-Step Flow

1. Generate ephemeral mTLS certificates

When azd app run starts, it generates a fresh Certificate Authority (CA), server certificate, and client certificate using ECDSA P-256 keys. These certificates are valid for 24 hours and are never written to disk outside of the container volume mount.

2. Start the mTLS auth server

An HTTPS server starts on localhost that only accepts connections presenting a valid client certificate signed by the ephemeral CA. This server proxies token requests to the real azd auth token command on the host.

3. Cross-compile the azd CLI shim

A lightweight Go binary is compiled for Linux (the container's OS). This shim mimics the azd auth token CLI interface but forwards requests over mTLS to the host auth server instead of trying to authenticate directly.

4. Configure the container

For each service with local.credentials: azd, the container is started with: the shim binary volume-mounted at /usr/local/bin/azd, client certificates at /run/secrets/azd-auth, and environment variables (AZD_AUTH_*) pointing the shim to the auth server.

5. Token flow at runtime

When your application code calls DefaultAzureCredential, the Azure SDK discovers the azd CLI on PATH and invokes azd auth token (the shim). The shim makes an mTLS request to the host auth server, which calls the real azd auth token and returns the Azure AD token to the container.

Configuration Reference

Credential forwarding is configured per-service using the local.credentials property in azure.yaml.

Property Type Values Description
local.credentials string azd Forward credentials using the azd developer CLI authentication
local.credentials string az (future) Forward credentials using Azure CLI authentication
local.credentials string auto (future) Use DefaultAzureCredential on the host, trying all available credential sources

Multi-Service Configuration

Only add local.credentials to services that actually call Azure APIs. Infrastructure containers like databases don't need it.

Complete Example

Security Model

Credential forwarding is designed for local development only. It uses multiple layers of security to protect your Azure credentials.

mTLS Transport Security

Property Value
Key algorithm ECDSA P-256
TLS version TLS 1.3 (minimum)
Certificate validity 24 hours (ephemeral)
Client authentication Required (mutual TLS)
CA scope Per-session, ephemeral, never persisted to system trust store

Additional Protections

Rate Limiting

30 requests per minute per client IP. Prevents credential abuse even if the mTLS cert is compromised.

Scope Validation

Only HTTPS URLs are accepted as token scopes. Input is validated for printable ASCII characters with shell injection protection.

Server Binding

The auth server binds to 127.0.0.1 on Windows and macOS (only reachable from the host). On Linux, the bind address is configurable to support Docker's networking model.

Certificate Cleanup

All ephemeral certificates are cleaned up when azd app run stops. They are never written to the system trust store.

Opt-in Model

Credentials are never forwarded unless the developer explicitly sets local.credentials: azd on a service.

⚠️ Trust Boundary

All containers with local.credentials: azd share the same trust boundary — they receive the same client certificate and can request tokens for any scope your Azure identity has access to. Only enable credential forwarding on containers you trust.

Troubleshooting

"azd auth token failed" inside the container

The most common cause is that you're not authenticated on the host. Run these commands on your host machine (not inside the container):

Rate limited (429 errors)

The auth server limits each client to 30 requests per minute. If you're hitting this limit:

  • Wait 60 seconds for the rate limit window to reset
  • Reduce concurrent Azure SDK calls during initialization
  • Cache tokens in your application (Azure SDKs do this by default)

Token works on host but fails in container

Ensure the container has local.credentials: azd set in azure.yaml, and that azd app run (not docker compose up) was used to start the services. The credential forwarding setup only happens through azd app run.
